Here we should give what actually elock do and why it scales so well. 

But this aproach would substantially complicated our production system design and would leave rather low capacity, lightly over 30% of the expected demand. So we were not sustisfied with it. 

The next aproach was based on the assumption that writing with batches may be cheaper. So we took our 10k clients back and let them to write 10 keys per transaction. Each client gets needed locks and do a batch write after. Yes, writing with batches is actually cheaper, but generally a client cannot know ahead what keys it will need to write, so it gets them in a random order and this leads to deadlocks. And deadlocks are expensive /home/roman/WORKTEMP/202610/elock_tests/2nodes/logs_10k_clients_100ts_10w, so even batching can overweight them. Elock degraded under this load, not heavily but enough. Mnesia surprisingly speed up still bihind elock, and what is important is it's restarts. The test's harness makes restarts 0 cost, but is it so for a real production system? Actually this aproach is an example of a bad designed system were even highly scalable lock engine can not always help. 

The next apraoch was based on our production system specific. About 99% of our writes go from our heavy runtime services (actors) like PLC connections, calculations, user scripts etc that produce derrived values. So, each service works with predefined set of objects and these sets don't intersect. But we also have ocasional writers like user processes and high level services like state estimation engine, AI agents (dispatcher assistant), electricity grid real-time graph etc, They can change setpoints, line states, change some settings or validate and rewrite some values. And they potentially conflict with our heavy writers, so we still need to synchronize writes between heavy runtime services and these ocasional writers. We applied the next aproach: each node starts all the configured services (read a node tries to get all the work), each runtime service on each node during start tries to get an exclusive cross-nodes lock on it's service object (for example PLC connection object). If succeeded it keeps the lock and continues to do a useful work with it's set of objects. If not it just hangs waiting for the lock. So finally we have runtime services ballanced across nodes and each has it's set of target objects. So they don't need to sync between each other, but still need to sync with the ocasional writers mentioned earlier. To resolve this we did a trick: heavy runtime service performs it's writes under shared local lock on each key and do it in batches. And each ocasional (rare) writer is required to get an exclusive cross-nodes lock on each key. This aproach gave us next results /home/roman/WORKTEMP/202610/elock_tests/2nodes/logs_10k_clients_100ts_10r. So this design met our demand with very big capacity over and ready to scale even further adding more nodes. As a bonus we also got 2 important features:
1. our load is well-ballanced across nodes
2. we got a free hot-redundancy. Because if some runtime service dies (with it's node or for some other reason) it's partner on the neighbouring node get's the lock at once and continues the work with almost 0 downtime.
